# Where to edit the program

There is one application. Every handwritten runtime, installer, probe and desktop
build source is under `source/`. The root Lua files, `data/matrix.lua`,
`deployment.json` and `dist/` are generated by the build.

## Handwritten source

| File / directory | Responsibility |
| --- | --- |
| `source/app/00_core.lua` | OC hardware calls, terminal discovery, NBT, persistence, energy and cooperative event handling |
| `source/app/10_plan.lua` | Assembly-line scan and rename plan |
| `source/app/20_apply.lua` | Shared donor supply, pattern editing, durable operation journal and recovery; assembly-line execution |
| `source/app/25_maker.lua` | Recipe scan and execution adapter using the common OC services |
| `source/app/30_ui.lua` | Common UI, buttons, scrolling, configuration and preview pages |
| `source/app/90_main.lua` | Application entry point |
| `source/lib/util.lua` | Shared value/collection helpers, identities, endpoints and text-row construction |
| `source/lib/config.lua`, `source/lib/programs.lua` | Unified settings and program definitions |
| `source/lib/batch.lua`, `source/data/tiers.json` | One shared batch policy and one versioned voltage-tier definition table |
| `source/lib/modes.lua` | Expands selected semantic recipe rules using the material matrix |
| `source/lib/planner.lua` | Pure destination capacity, reuse, sorting and creation planning |
| `source/lib/preview.lua` | One maker preview renderer used by the UI and exported report |
| `source/launcher.lua`, `source/install.lua`, `source/interface_probe_src.lua` | Launcher/updater entry, installer, and interface probe sources |
| `source/tools/` | Desktop scrape import and matrix compilation |
| `source/build.js`, `source/test.js`, `source/build.ps1` | Desktop build and test entry points |

The numbered `source/app/` files are sections of a single lexical
scope. They are not individually loadable modules. `source/lib/` contains modules,
embedded once by the build. This distinction is
important when moving functions: a section-local function can be used by later
sections. Shared general helpers are explicitly called through `U`.

## Generated files and what runs on OC

`npm run build` produces these root staging artifacts:

- `assline.lua` from `source/launcher.lua`: the small stable launcher.
- `assline_app.lua` from `source/app/` and `source/lib/`: the complete application.
- `assline_data.lua` from `data/matrix.lua`: the semantic material/rule data.
- `interface_probe.lua` from `source/interface_probe_src.lua`: the diagnostic tool.

The same build copies them, plus generated `install.lua`, into `dist/` and generates
`dist/release.manifest` and `deployment.json`. **OC downloads from `dist/`.** The
installer places the application in `/home/assline/releases/<release>/`; the
stable `/home/assline.lua` launcher selects the active release. Config and
recovery files live outside the versioned release directory.

The root and `dist/` copies are build outputs, not independently maintained
implementations. Edit the source listed above, then rebuild. Root staging copies
remain because the build/test harness uses them; they are not additional apps.

## Reading the matrix

`data/matrix.lua` is itself generated by the desktop compiler. It contains shared
form resolvers, registry spellings, material rows, capability sets, production
flags and generic recipe rules. It does not contain a full recipe list for each
material. See [PATTERN_MAKER.md](PATTERN_MAKER.md) for the import commands.

`capabilities` is an array of deduplicated sets. Each entry is a dictionary such
as `{ingot=true, wireFine=true, ...}`. A material's `a` field is the index into
that array; multiple materials can point to the same set. The lookup is:

```lua
local supportedForms = data.capabilities[material.a]
local hasFineWire = supportedForms.wireFine == true
```

These sets describe registered item forms. They do not, by themselves, prove
that a machine recipe exists. The separate shared production flags and scraped
rule requirements decide which transformations are allowed.

`usage` is another deduplicated set array. A material's `u` indexes output
forms that reach a non-recycling product through the full recipe export.
`source/tools/build_usage.py` creates that evidence on the desktop; `source/tools/compile_matrix.py`
embeds only the shared form sets. `source/lib/modes.lua` applies the same exclusion to
all program modes and records the skipped material/forms in the preview.
`source/app/25_maker.lua` compares occupied destination patterns with that list and the
planned recipes to show why each pattern is reused or preserved. This diagnosis
uses the already read terminal snapshot; it makes no extra component calls.
`source/lib/preview.lua` formats the same capacity, plan, Existing and Excluded
rows for both screen and exported text. Change wording there once.

The pinned BartWorks enum omits some registered materials. The desktop form
import discovers missing Werkstoff suffixes only when the full resource index
has both an ingot with a material display name and a matching plate. This
recovers Mu-metal (suffix 11351) and its scraped bending and use evidence.

## Recipe proportions and configured batches

`source/lib/planner.lua` owns recipe identity. For processing patterns it aggregates
identical ingredients, finds one greatest common divisor across all input and
output quantities, then builds the signature from those reduced quantities.
It returns that divisor separately. Matching signatures mean the same recipe;
different divisors mean the same recipe needs a batch-size edit. Crafting grid
identity remains exact. NBT, item/fluid identity and substitution flags remain
part of both comparisons.

`source/lib/modes.lua` applies the program's multiplier to the selected rule's encoded
inputs and outputs. The planner prefers an exact batch if several equivalent
patterns exist, otherwise schedules a resize after sorting. The adapter sends
both new imprints and resizes through the same editing function; the shared
executor journals the original pattern and requested quantities for recovery.
Resizing uses the pattern already in the destination, not a disposable donor.
`source/lib/batch.lua` computes the per-recipe multiplier once, before ingredient
resolution. Fixed batching preserves earlier settings. Tiered batching combines
relative material budgets, optional absolute tier overrides, recipe voltage,
program factors and quantity limits. `source/data/tiers.json` is read by both
the desktop tools and bundle builder; the voltage names/thresholds are not
copied into a second hand-edited table. The compiler keeps a common EU/t on
each semantic rule and interns sparse voltage exceptions into shared sets.
`source/tools/build_tiers.py` scrapes quest requirements. The generated
`data/material-tiers.json` is desktop provenance, and only its tier values and
source summary are included in the OC matrix.
The maker adapter reads both encoded item layouts: older entries store a
positive `Count`; newer entries store `Cnt` while leaving `Count` at zero.
It falls back to OC's converted `size`/`amount` when the raw entry lacks a
positive count. The same normalization is used for edit read-back and recovery.
An unreadable count leaves that pattern unmatched with a reason in Existing,
instead of stopping the whole scan.

For the bending program, `source/tools/compile_matrix.py` imports only the selected
one-solid routes with a stocked integrated circuit. Its 18 shared rules cover
ingot/plate routes for plates and foil, plate-fed sheet metal, and rod/wire-fed
springs. Each material receives production flags only for routes actually
present in the scrape. Distinct small-spring yields have distinct flags.
`source/lib/programs.lua` defines output switches, source selectors and destinations;
`source/app/25_maker.lua` passes those selections to the same compiler and planner used
by wiremill. A disabled output leaves any existing pattern untouched as a
foreign pattern in the destination layout.

Fluid Shaper uses the same planner and durable editor. Its compiler imports
only Fluid Solidifier recipes with one molten input, one reusable GT mold and a
registered solid output. Each material stores its primary molten-fluid ID,
while shared rules describe the mold shapes. The OC pattern setter receives a
fluid stack for the requested input; the mold remains external stock. Settings
page through mold fields with adjacent enable switches. Fluid and item pipes
share a switch and destination when they use the same mold. Extruder ingot
recipes remain a separate route.

## Donor refills and safety boundaries

Preview fixes destinations, recipe identities and sorting operations. Donor
availability is advisory and is deliberately excluded from stale-preview
comparison. Destination/editor changes still invalidate a preview.

Both executors use the same `donorPool` in `source/app/20_apply.lua`. It discovers exact
names through the terminal, caches candidate slot references, and rereads a donor
before use. It does not retain all donor NBT or rescan every bank per pattern.
When exhausted, it retries discovery after a one-second cooperative wait. The
existing event loop handles Cancel/Escape during that wait.

The pool waits before writing an operation intent. Cancelling a refill wait
therefore needs no recovery; completed patterns remain installed. A fresh preview
reuses them. Once an intent exists, the existing operation/recovery code owns
that exact physical donor and keeps its original validation behavior.

## Formatting and test evidence

Use StyLua 2.5.2 with the checked-in configuration:

```text
stylua --verify source/app source/lib
npm test
```

`--verify` checks formatting against the original syntax tree. Functional tests
exercise the generated bundle, pure planner/compiler, installer and scrape tools.
They are contract simulations, not an embedded Minecraft server. In particular,
the ultimate-pattern fixture was constructed from upstream code after the live
bug report; it is not captured NBT from the user's game. Those tests demonstrate
the expected handling and recovery, not independent proof of the mock's accuracy.

The relevant upstream implementations are OC's
[ingredient setter](https://github.com/GTNewHorizons/OpenComputers/blob/master/src/main/scala/li/cil/oc/integration/appeng/internal/PatternEnvironment.scala),
[pattern converter](https://github.com/GTNewHorizons/OpenComputers/blob/master/src/main/scala/li/cil/oc/integration/appeng/ConverterPattern.scala),
and AE2's
[ordinary pattern helper](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial/blob/master/src/main/java/appeng/helpers/PatternHelper.java)
and [ultimate pattern helper](https://github.com/GTNewHorizons/Applied-Energistics-2-Unofficial/blob/master/src/main/java/appeng/helpers/UltimatePatternHelper.java).
These links identify the inspected upstream behavior, rather than claiming a
captured integration test against the installed pack.
